# 刻迹 CLI — MVP 规划

> 定位：自用工具 + 数据采集器。不进商业化路径。
> 与 `刻迹-PRD-v0.1.md` 的关系：本阶段产出的 SQLite 就是 App 阶段的数据底座。

---

## 0. 先做探针（半天，代码全部丢掉）

整个 MVP 的可行性压在三个未知上。写三个一次性脚本验证，不要写任何正式代码。

三个探针**两个工具各做一遍**，结论很可能不一样。

**探针 A — 限额读取通道**
不碰 token 日志，直接验证两条通道能不能拿到「剩余百分比 + 重置时间」。

Claude Code：写一个最小的 statusline 脚本，把 stdin 收到的完整 JSON 原样 dump 到文件，看里面有没有 `rate_limits`，以及它包含哪些桶。你机器上的版本是什么行为，以 dump 出来的为准。

Codex：确认 CLI 内部用的那个用量端点能不能拿本地凭据直接调通，返回结构长什么样。调不通就退化成解析 `/status` 的输出。

两边都要记下**桶的完整清单**：5 小时、周、按模型分的、以及 Codex 那个独立的 code review 周限额。这决定了数据模型是一行还是一组行。

**探针 A 的结论比另外两个都重要。** 通道拿不到就整个改成手动登记，产品价值会掉一大半。

**探针 B — 阻塞信号**
故意把一个窗口跑到限流，记录三件事：CLI 的报错原文、退出码、有没有给出重置时间。这是功能 3 的全部地基，拿不到重置时间就得退化成轮询试探。

**探针 C — 无头执行与续接**
验证 `claude -p` 一类的非交互模式能不能在脱离终端的情况下跑完一个任务，输出里能不能拿到 session id，以及拿这个 session id 能不能续接一个中途被打断的任务。

三个探针都通 → 按下面做。探针 B 拿不到重置时间 → 功能 3 降级为「重置时间由用户配置 + 定时试探」，仍然可做。探针 C 不通 → 整个队列不成立，回去做 App。

## 1. 分三步交付

### v0.1 只读仪表（1–2 个晚上）

一个命令：`keji status`

输出每个桶的剩余百分比和重置倒计时，以及**当前的绑定约束**——所有桶里最接近零的那个。Claude 侧如果 `representative-claim` 有值，以它指向的窗口为准。

不做队列，不做执行，只采样和展示。

**没有上限学习机制，也不需要。** 官方已经把百分比算好了，自己反推天花板是多余的一层误差。

**但显示值不是执行许可。** 两边的仪表和真实拦截经常不一致，所以 v0.1 只把这些数字当规划参考，永远不用它来判断「这个任务能不能开」。真正的判据在 v0.2 的阻塞事件里。

### v0.2 队列与阻塞恢复（核心，MVP 的重心）

```
keji add "重构 payment 模块的错误处理" --repo ~/code/paycore
keji add "给上一步写单测" --after 3
keji ls
keji run        # 守护进程
keji logs 3
```

守护循环的逻辑：

1. 取一个可执行任务（依赖已完成、未被阻塞）
2. 决定用哪个工具：任务显式指定则用它；指定的工具余量不足且任务标了 `--any-tool`，则派给另一个有余量的
3. 乐观开工：仪表显示余量为零时才不开，其余情况一律试。**不拿百分比做准入门槛**，因为它和真实拦截经常不一致，卡在这里会白白空转有余量的窗口
4. 无头执行，实时记录 session id 和所用工具
5. 执行结束：正常完成则采样一次各桶余量；撞限流则标记为 blocked，写入重置时间
6. 阻塞后休眠到重置时间 + 随机抖动，醒来续接
7. 续接**必须**用 session id 恢复原会话，重新开一个会话等于把上下文再烧一遍，这是最容易犯的错

**阻塞事件是唯一可信的信号。** 仪表负责让你知道大概还能干多久，阻塞事件负责让队列做出正确决定。两者不要混用。

**跨工具降级只发生在第 2 步。** 已经跑了一半的任务不能换工具，因为 session 上下文带不过去，只能睡到重置。想让一个任务可以冷启动重跑，得在 `add` 的时候就标 `--any-tool`，等于声明「这个任务丢掉上下文重来也没关系」。

任务状态机：`pending → runnable → running → blocked → done / failed`

`blocked` 和 `failed` 必须分开。前者自动恢复，后者需要人看。

### v0.3 后继任务（1 个晚上）

每个任务带一个 `on_success` 钩子。钩子的产物不是直接执行命令，而是**往一个约定路径写一份新任务的 JSON**，守护进程下一轮扫描时摄入。

这样绕开的坑：让 AI 直接生成并执行 shell 命令，等于给一个无人值守的循环开了任意代码执行的口子。中间垫一层可检查的声明式文件，出问题时你能看到它想干什么。

加一条硬约束：自动生成的任务不能再自动生成任务，链深度上限为一。否则半夜可能给你跑出一棵指数膨胀的任务树。

## 2. 数据模型（够 MVP 用的最小集）

SQLite，五张表。

| 表 | 关键字段 |
|---|---|
| `task` | prompt, repo, tool, any_tool, session_id, state, depends_on, on_success, priority, created_at |
| `run` | task_id, tool, started_at, ended_at, exit_code, blocked, session_id |
| `bucket` | tool, bucket_key（如 `claude:5h`、`codex:weekly`、`codex:review_weekly`）, is_representative |
| `sample` | bucket_id, at, remaining_pct, reset_at, source |
| `event` | type, tool, bucket_id, at, payload |

**限额是一组桶，不是一个数。** `bucket` 存清单，`sample` 存时间序列，两者分开，这样以后加桶不用改结构。任何「还剩多少」的查询都是取各桶最新 sample 的最小值。

**不存 token 计数。** 你不关心消耗了多少，只关心还剩多少，而剩余量是官方直接给的。省掉这一层等于省掉整个日志解析模块。

`run` 表只记「跑了没、被拦了没」。一个任务对多次运行（因为会被阻塞重跑），所以 `task` 和 `run` 必须分开，别图省事合成一张。

`event` 的 type 至少包含：`rate_limit`、`window_reset`、`sample_failure`、`task_blocked`、`task_resumed`、`tool_switched`。这张表是后面 App 做复盘的原料，宁可多记。

## 3. 明确不做

单文件二进制、无 TUI、无 Web、无守护进程管理框架（launchd 一行搞定）。

工具范围就是 Claude Code 和 Codex 两个，MVP 内都要有。不做 Cursor、Gemini，也**不做手动打卡**——两边都有可读的限额通道和无头模式，手动兜底这条整个可以砍掉，比 App 那版省一大块。

也不做日志解析。既然剩余量能直接读到，就没有必要去碰会话 JSONL，那一层是纯负担而且格式变得最勤。

但接口要照着两个工具一起设计，实现分先后落地：先把 Claude Code 端到端跑通，再接 Codex。反过来只写一个就抽接口，抽出来的一定是 Claude Code 形状的，接第二个时得推倒重来。

不做美元成本换算。订阅用户不关心钱，关心的是窗口里还能干多少活。

---

## 4. 无人值守的安全约束

这一节不是可选项。一个跳过权限确认、在你睡觉时自动开跑的 AI 循环，是真的能搞坏东西。

- 每个任务在独立的 git worktree 里执行，不在主工作区
- 禁止任何 push、禁止碰远端分支、禁止改 CI 配置
- 任务完成只提交到本地分支，人工 review 后才合并
- 守护进程带全局熔断：单窗口内失败任务数超阈值就停机等人
- 敏感目录白名单，`--repo` 之外的路径一律拒绝

## 5. 三个月后的收敛点

CLI 跑满一个季度，你手上会有：各个桶的余量时间序列、阻塞发生的时间规律、两个工具窗口的错峰程度、跨工具降级的实际触发频率。

这些数据决定 App 那一版的三件事：配额时钟的耗尽预测是否可信、空窗建议该怎么排序、以及「人机时间比」这个指标到底有没有说服力。

「两个工具的窗口有多错峰」这一条尤其值得盯。如果实测下来错峰明显，跨工具降级就是刻迹最硬的卖点；如果两边总是同时耗尽，那功能 3 就只剩「睡到重置」，产品叙事得重写。

在此之前不动 App。
