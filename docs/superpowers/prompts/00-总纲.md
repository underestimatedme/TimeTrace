## 产品契约（三端必须一致）

以下是设计稿已经定稿的结构。三个仓库的命名、层级、状态机都要对得上。

### 导航：底部五入口

```
今日 | 项目 | 时间线 | AI | 我的
```

- **报告**不是底部入口 —— 从「今日」页**右上角**进入，返回时回到来源页
- **项目报告**是另一个入口 —— 从项目详情页进入，其列表、统计、Markdown 导出
  都**限定当前项目**（规则见 `design/src/review/reportScope.ts`）
- **个人中心**从「我的」进入；所有子页（资料、设备、隐私、主题动效、
  首页内容、通知、帮助反馈）返回「我的」，且保留底部导航

### 三级数据模型

```
项目 (Project) → 任务 (Task) → 计划 (Plan)
```

Plan 承载：所选 AI 工具、优先级、执行策略、依赖关系、验收条件。
依赖未验收时，后继 Plan 不可执行（UI 上禁用并说明原因）。

### 人 / AI 双轨

时间线与报告都按「我」和「AI」两条轨道呈现，可切换、可按项目筛选、可切日 / 周。
等待时间是独立的第三类，不属于任何一方的工作时间。

### 验收闭环

Plan 执行完成后进入「结果待确认」（**不是**「处理中」——
这个措辞是设计稿明确改过的），逐项勾选验收条件，全部勾选才能提交，
提交后周目标进度与报告同步更新。

### 工具额度四层级

四个 AI 工具按能力分层，额度有周限额。额度耗尽时 Plan 进入等待而**不是**
转为付费执行。额度恢复后可续跑原会话；自动续跑开关关闭时，
恢复只补额度、不自动运行，需在 Plan 详情手动继续。

## 一条不可违反的数据契约：phase-facts-v2

后端刚刚完成日报的重构（Valley commit `95bd8d8`，baseline 标识
`reportBaseline = "phase-facts-v2"`）。核心变化：

**报告不再累加时长，而是记录「相位事实区间」。未知不等于零。**

```go
type ReportPhaseFact struct {
    ID     string    `json:"id"`
    TaskID string    `json:"task_id"`
    Track  string    `json:"track"`  // human | ai | waiting
    State  string    `json:"state"`  // known | unknown
    Start  time.Time `json:"start"`
    End    time.Time `json:"end"`
}
```

`DailyReport` 的 JSON 序列化会把**无法测量的字段返回 `null`**，而不是 0：

- `human_seconds` / `ai_seconds` / `waiting_seconds` —— 该轨道存在 `state != "known"`
  的事实时返回 `null`
- `estimated_value_minor` / `actual_spend_minor` —— 目前**没有任何金额测量来源**，
  恒为 `null`

**因此，所有客户端（iOS、Forge）必须：**

1. 把 `null` 渲染成「未测量 / 数据不足」之类的明确文案，**绝不渲染成 `0` 或 `0h 0m`**
2. 不对 `null` 做求和、求平均、算百分比
3. 样本不足时不显示总分（设计稿已明确：「样本不足不显示假总分」）

这不是风格偏好。把未知显示成零，就是在伪造生产力数据 —— 这个产品的全部价值
建立在数据可信上。

每一项功能改动都要：先写一个能复现「当前还做不到」的测试并看到它失败，
