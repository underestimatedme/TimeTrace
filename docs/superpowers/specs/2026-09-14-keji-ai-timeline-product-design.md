# 刻迹：个人与 AI 多项目时间线管理设计

日期：2026-09-14。状态：产品设计与交互原型已更新，待评审；未修改生产 iOS、Valley 或 CLI 功能代码。

评审入口：[交互原型](http://127.0.0.1:5194/review) · [代码修改总计划](../plans/2026-09-14-keji-ai-workspace.md)。原型实现主路径与代表性等待/验收状态；完整创建编辑、周视图与真实数据接入见实施计划。

## 1. 定位与已确认约束

刻迹服务于同时使用多个 AI 工具推进多个项目的个人开发者。核心承诺：围绕交付目标安排自己和 AI 的工作，知道下一步该做什么、由谁做、何时能继续，以及今天实际交付了什么。

用户确认：自动续杯指订阅额度自然恢复后自动续跑暂停的 Plan，不额外付费。本文不把恢复额度理解为购买额度、兑换券或重新订阅。

业务层级固定为项目 → 任务 → Plan；目标是项目的版本/里程碑属性与任务分组，不增加第四级目录。产品导航围绕今日、项目、时间线、AI、报告展开。

## 2. 产品路径选择

| 路径 | 优势 | 局限 |
| --- | --- | --- |
| 额度仪表盘 | 最快提供重置倒计时与提醒 | 无法解释额度对项目交付的价值 |
| 目标驱动的个人与 AI 工作台（推荐） | 将目标、排程、验收、额度连接起来，复用现有 Runner | 需要新增 Plan 与调度规则 |
| 全自动项目工厂 | 自动拆分、分派、审核、发布 | 现阶段缺少质量与成本证据，自动化失败影响更大 |

采用第二条。先建立可解释的推荐与受控续跑，用真实验收数据逐步改善分派。

## 3. 已有基础与准确的差距

- iOS 已有 Project、Goal、TaskItem、TimeSession、AIExecution，以及今日/任务/时间流/洞察/我的页面。
- Claude/Codex 本地适配器已有 quota sample、start/resume；scheduler 已有依赖、额度等待、会话恢复与熔断。
- Valley + 本机 Runner 已形成远程派发基础。既有工具凭据仍留在本机。
- 当前 TaskItem 直接关联执行，没有独立 Plan；AIToolConnection 仅表达连接状态，不能描述账号、模型和共享额度。
- 当前本地 scheduler 将未知额度按满额参与排序；已过 reset_at 的限额样本不再阻塞。这只是本地启发式，不能在新 UI 中显示为“实测已恢复”。
- 本地 scheduler 与远程 Agent 都有执行相关逻辑，新设计必须协调成同一执行入口，不能各自重复领取/启动。现有基础不等于已实现本文完整的端到端自动续跑。
- 本轮只核对相关代码与资料，没有重新验证所有线上能力。

## 4. 工作对象

项目：仓库关联、项目价值、当前版本目标、目标日期、范围、默认执行策略、运行权限。

目标：例如“本周五前交付 v1.2”，记录必须完成的任务、验收条件、目标时间、范围变更与交付证据。目标可以关联多个任务；任务首版仅绑定一个主要目标，避免重复计算进度。个人周目标通过汇总多个项目里程碑表达。

任务：可交付的业务结果，例如“支持多 AI 额度看板”。包含价值、紧急程度、难度、风险、优先级 P0–P3、预计工作量、依赖与验收条件。

Plan：一次可验收的执行单元，例如“实现额度数据结构与迁移”“完成倒计时界面”“验证跨窗口恢复”。包含输入、预期输出、验收项、预计人工时间与 AI 活跃时间、依赖集合、执行人/工具/模型、首选与备选策略、是否允许自动续跑。Plan 内可以有步骤清单，但不再增加管理层级。

ExecutionAttempt：Plan 的执行记录，包含 Runner、工作目录、厂商会话、开始/结束、等待原因、测试证据、成本来源。限额中断和恢复产生多个 attempt，仍属于同一个 Plan，不重复计算交付量。

工具与模型分开：Cursor/Codex/Claude Code/Gemini CLI 是工具入口；具体模型是执行配置；账号与订阅决定使用哪个额度池。同一个模型从不同工具使用，可能消耗不同额度。

示例：

```text
刻迹项目（目标：本周交付 v1.2）
  任务：多 AI 额度管理 · P1
    Plan：额度结构与数据采集 · AI 执行
    Plan：额度卡片与倒计时 · AI 执行
    Plan：验收未知/过期/恢复场景 · 人工 + AI
  任务：每日开发报告 · P2
    Plan：聚合已验收工作记录
    Plan：生成与审阅 ChangeLog
```

| 主入口 | 首要信息 | 核心动作 |
| --- | --- | --- |
| 今日 | 本周关键目标、今日推荐、个人/AI 运行摘要、待审核 | 开始我的工作、派发、验收、调整今日安排 |
| 项目 | 各项目的版本目标、交付进度与风险 | 进入项目 → 任务 → Plan；编辑目标范围 |
| 时间线 | 人工工作、AI 并行执行、等待额度、等待审核、重置事件 | 缩放时间、按项目/执行者过滤、调整未开始计划 |
| AI | 工具账号、各额度窗口、恢复时间、排队工作、公共信号 | 查看推荐用途、调整续跑策略、连接电脑 |
| 报告 | 每日 ChangeLog、目标贡献、生产力评分、质量与费用趋势 | 核对证据、纠正归属、导出日报 |

账号与外观放到头像入口，AI 管理由二级设置提升为主导航。现有任务列表成为项目内列表与“全部任务”筛选视图。

今日首屏结构：日期/头像 → 一个重点版本目标 → 横向 AI 可用性摘要 → “你现在最值得做的事” → 正在运行 → 待你审核。详细统计下沉报告，避免首页同时堆积多个仪表盘。

视觉采用中性背景、清晰文字、轻量卡片。品牌主色从用户最终 Logo 取样后确定；不靠工具品牌颜色表示成功/失败。状态同时使用文字与图形，支持动态字体和深色模式。AI 卡片的额度百分比、倒计时采用等宽数字。

时间线保留人工和各工具的独立轨道。手机默认显示“我 + 当前关注 AI”，其余轨道折叠为运行摘要；展开后可纵向查看全部。个人工作用实心区间，AI 执行用带执行者标记的区间，等待用斜纹，重置用事件节点，未来计划用虚线。所有区间均有文字状态，不只靠颜色区分。

支持关注项目的周视图：目标期限与关键依赖一起显示。额度恢复节点投影到未来时间线上，并注明“预计/已确认”。人工时间不与并行 AI 时间简单相加；分别显示人工投入、AI 累计活跃、项目实际历时、等待时间。

## 6. 评分：排序、分派与成果分开

优先级 P0–P3 可人工固定；AI 仅提出解释与调整建议。未就绪依赖、缺少授权、等待人工输入等是硬阻塞，高分不能越过。

任务优先分（建议初始规则，0–100）：35% 目标贡献 + 30% 截止紧迫度 + 20% 解锁后续工作价值 + 15% 等待时长。各维度使用公开量表归一化；优先级先分组，分数只用于组内排序。相同分数按入队时间稳定排序。评分带版本与理由，避免暗中变化。

难度/风险另记 1–5 级：涉及代码范围、需求不确定性、验证难度、回滚难度。高风险任务通常需要更严格验证和人工审核，不直接等于更高业务优先级。

AI 分派：先筛选能力、可用账号、运行权限、数据访问范围、依赖、是否允许额外费用；再综合相似任务验收通过率、预期完成时间（含等待额度与审核）、额度消耗、上下文复用与返工风险排序。Task 提供默认策略，Plan 可覆盖，展示首选、备选及理由。

模式：均衡（默认）、速度优先、节省额度、手动指定。即使速度优先，也遵守用户“零额外付费”的硬限制。订阅成本与新增付费分开：已支付的月费不伪装成每个 Plan 的实际账单；可选分摊显示为估算，API 等价金额也不得标注成实际支出。

冷启动没有用户历史时采用可编辑的能力规则和区间估计，标记“样本不足”；不预先认定某品牌一定擅长某类任务，也不展示虚构成功率。后续按工具 + 模型版本 + 任务类型更新统计，并显示样本量。

订阅额度百分比不能跨厂商直接比较，更不能将 30% 额度兑换为固定 tokens。资源紧张时优先保证关键目标，给低优先级任务设置等待上限和可配置份额，避免长期饿死。

完成质量记录验收项、测试/构建证据、人工是否接受、返工次数。生产力分建议采用：目标贡献 45%、质量/验收 30%、计划兑现 15%、资源效率 10%。权重是产品初始假设，需要真实使用验证。

生产力评分以预先确认的范围/工作量为基准，不能通过拆成大量小 Plan 刷分；单项贡献在其任务权重内封顶。缺失维度标记未知并降低覆盖率，不当成 0 或 100；数据覆盖不足时只展示分项与原因。评分仅用于个人趋势，不衡量人的价值。AI 时间、tokens、代码行数不直接计为正向产出。等待审核不计入已验收交付。

## 7. 额度与 BetterOPC 信号

个人额度样本保存：account/profile、quota_pool、限制适用范围、窗口类型、已用/剩余、reset_at、采样时间、来源、置信度、计费模式。字段允许 unknown；读取失败不等于满额。多个工具共享同一账号额度时合并池，不能重复估算可用容量。

窗口类型可扩展：短时、周、日、月、模型专属、组织共享等，不把所有工具写成固定五小时。恢复时间使用厂商返回的时间和时区；不知道时显示未知。多个约束同时耗尽，只有所有适用阻塞均解除才可运行。

BetterOPC 在本次访问结果中展示 Codex、Claude Code、Grok Bot 的公共重置及活动信号，并区分确认/可能等状态。抓取页面标注更新日期为 9 月 8 日，不能把其中“今日”当成 9 月 14 日。它不是个人账号额度接口。

接入路径：优先核实并使用公开或获授权的数据接口；本轮尚未确认公开 API。如果没有，则评估允许的服务端低频抓取/缓存，先提供原页面链接作为降级。Valley 集中采集，各手机读取同一缓存。外部故障不得阻断个人额度和本地任务调度。

只保存必要的事件摘要、来源链接、发布时间、生效时间、适用套餐、确认程度和采集时间；按源事件去重、处理更正与过期。展示来源归属；不整站复制。文案属于外部数据，不能作为执行器指令。

“官方公告重置”触发一次账号额度刷新；只有个人状态确认恢复，或符合受控试跑条件，才能恢复 Plan。“可能重置”只提示，不解除额度阻塞。公告时间与个人配额的实际生效时间分开。

## 8. 自然恢复后自动续跑

```text
执行中 → 额度受限 → 保存恢复信息 → 等待额度
                                  ↓ 到期/可信公共信号
                             刷新账号状态
                                  ↓ 可运行
                            重新评估优先级
                                  ↓ 轮到此 Plan
                     原工具、原会话、原工作目录续跑
                                  ↓
                           待验收 → 已完成
```

恢复信息包括会话标识、工作目录与提交状态、已完成验收项、最后有效输出、失败原因、已发生副作用、attempt 标识。CLI 原生会话恢复能力由适配器明确声明；不支持时不能把新开会话当成无损恢复。

恢复前检查账号有效、电脑在线、没有其他进程占用同一 Plan/工作区、租约有效、依赖仍成立、用户没有取消、权限与零额外付费策略仍满足。取消后不得被旧的恢复定时器唤醒。网络恢复补报、进程崩溃和额度恢复分别处理。

精确读取额度不可用时：到可靠 reset_at 后允许单次受控恢复尝试，必须确认该执行通道不会自动转入额外计费；继续限额则记录新等待时间并退避，不无限重试。无法保证计费边界或会话安全时等待人工处理。新 UI 在尝试前显示“预计恢复，待验证”，而不是“已满额”。

配额是账号级资源；同一账号跨电脑采样与恢复需在 Valley 统一协调。避免两台 Runner 在同一恢复时刻重复启动。首版延续每台 Runner 单个编码进程，不因多轨道 UI 暗示当前已支持多进程；多电脑可形成并行轨道，后续按账号与仓库限制逐步开放并发。

另一个 AI 可以接未开始且适配的 Plan；已经开始的 Plan 默认保持原工具/会话。跨模型交接需要独立的交接摘要、文件版本、验证结果与新的 attempt，不能假设共享隐藏上下文。

零额外付费策略不仅检查“不要购买”：还需识别已启用的自动充值/超额用量及 API 计费回退。只有适配器能验证或强制限制新增支出时，才标记“可无人值守续跑”。不支持的入口退化为管理/提醒；这项能力必须按工具实测。

Valley 持久化恢复时间和排队状态，本地 Agent 执行。iOS 被关闭不影响云端队列，但本机休眠、离线或登录失效会延后执行；通知准确显示阻塞原因，不承诺手机后台承担定时执行。

## 9. 开发日报与 ChangeLog

按用户时区每日生成项目分组的私有日报：已验收成果、待验收变更、阻塞与返工、目标进度变化、明日建议、人工时间、AI 活跃与等待、可核实的费用/额度。

来源是已关联的 Plan 事件、commit/PR、构建和测试证据、人工验收。每条成果可追溯；同一个成果的多个 attempt 不重复计数。未提交的改动、AI 自报完成、已合并、已发布采用不同状态；AI 生成自然语言不改变事实状态。

自动生成的是开发日报和 ChangeLog 草稿。写入仓库 CHANGELOG.md、创建 release 或发布对外报告是单独动作。无执行记录的日子显示“无记录”，不推断没有工作。补到的离线事件生成修订版，保留原记录。

日报本身遵守额度与成本策略：先用确定性模板聚合；需要 AI 润色时作为低优先级内部作业使用允许的订阅资源，额度不足延后。避免为报告创建付费 API 调用，也避免让“生成日报”反向刷高生产力分。

## 10. 实现模块与迁移

复用现有 iOS → Valley → 本机 Agent 架构。新增/扩展：Plan、PlanDependency、ExecutionAttempt、AccountQuotaPool、QuotaSample、ResetSignal、DispatchDecision、DailyReport；Goal 延用并补充范围及验收证据。

Valley 负责计划、权威执行状态、到期队列、账号额度协调、公共信号缓存与报告事实聚合；Agent 负责工具适配、额度读取、原生 resume、本地代码与验证；iOS 负责规划、解释推荐与验收。

旧任务没有 Plan 时生成“执行此任务”默认 Plan，将原执行记录挂到该 Plan，保持 task_id 不变。旧 TimeSession 可暂留 task_id 并新增可空 plan_id，避免破坏历史数据。新记录按 Plan 归属聚合，防止任务与 Plan 双计。

接口和本地持久化需要版本化迁移；旧客户端应保留读取能力，不能用旧 sync 快照覆写新 Plan 的服务器执行状态。依赖关系防环；跨项目依赖必须显式建立。

## 11. 交付顺序与验收

1. 产品骨架：项目 → 任务 → Plan、版本目标、今日页和人工/AI 时间线；已有记录迁移且统计不重复。
2. Claude/Codex 闭环：个人额度、等待恢复、原会话续跑、Runner 与计费能力验证。先贯通一个真实 Plan 的中断/恢复/验收，再扩充自动化。
3. 评分与日报：优先分解释、手动覆盖、验收证据、目标进度和有来源的日报；缺失数据明确显示。
4. 多工具扩展与信号接入：Cursor、Gemini 按适配器能力逐步上线；公共信号采集独立验证，不能阻碍前面模块交付。

每项工具在 UI 上分别标注“可记录”“可读额度”“可派发”“可恢复”，不以一个“已连接”承诺全部能力。首版可先管理所有工具，仅对已验证工具开放自动派发。

关键场景验收：五小时窗口恢复但周额度仍耗尽时不执行；未知/陈旧样本不显示满额；公共可能信号不解锁；重复公告不重复启动；断网重连不双计；取消后不恢复；多机共享额度不双派发；同工作目录无并发写；恢复失败保留检查点；无额外计费保障时不自动启动；旧客户端不覆盖新状态；日报跨时区且成果可追溯。
